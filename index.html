💥 Scenario 1: Unbalanced Colocation

Both Kafka & EDB Postgres are pinned to worker node minikube-m02 via nodeSelector.

Node: minikube-m02 (Worker) CPU/IO Overloaded (98%)
📬 Kafka Broker (Strimzi) Req: 1.2 CPU | 1.5GB RAM
🐘 EDB PostgreSQL (CloudNativePG) Req: 1.2 CPU | 1.0GB RAM
Node: minikube (Control-Plane) Idle (8% Usage)
No application workloads scheduled
⚠️ Impact: CFS CPU throttling delays PostgreSQL WAL writes. Kafka message flush serializes with Postgres queries, dropping TPS by 70%.
🛡️ Scenario 2: Pod Anti-Affinity Resolution

Workloads enforce mutual exclusion via podAntiAffinity across kubernetes.io/hostname.

Node: minikube Balanced (50% Usage)
📬 Kafka Broker (Strimzi) Dedicated 2 CPUs & 4GB RAM
Node: minikube-m02 Balanced (52% Usage)
🐘 EDB PostgreSQL (CloudNativePG) Dedicated 2 CPUs & 4GB RAM
✅ Result: Zero CPU throttling. Dedicated Linux page cache & disk I/O queues. Stable latency and 4x TPS throughput.

🧠 Root Cause Analysis: Why Colocating Kafka & Postgres Fails

Both Apache Kafka and PostgreSQL are high-throughput stateful data services with distinct, aggressive I/O profiles:

  • Page Cache Invalidation: Kafka relies heavily on the Linux OS Page Cache and sequential append-only writes, while PostgreSQL relies on both its internal shared buffers and filesystem caching. When sharing a node, Kafka flushes can evict PostgreSQL working memory pages from the kernel cache.
  • CFS Quota Throttling: Under CPU resource limits, the Linux Completely Fair Scheduler (CFS) enforces quotas over 100ms periods. Heavy Kafka message compression and simultaneous Postgres query planning trigger aggressive CFS throttling.
  • WAL fsync Stalls: Both workloads write write-ahead logs (WAL) to disk requiring fsync calls. On a single node disk, WAL flushes queue behind Kafka segment commits, causing dramatic latency spikes.
